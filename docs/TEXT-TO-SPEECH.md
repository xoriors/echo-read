# Text to speech: how it works today

**Short version: it is entirely cloud. Nothing is synthesised on the device.**
Every second of audio is generated by Google's Gemini API, relayed through this
server. The browser only decodes and plays.

If you are here to find out whether user text leaves the machine: it does. Jump
to [What leaves the device](#what-leaves-the-device).

---

## The path a sentence takes

```
BROWSER                          SERVER (Fly, fra)              GOOGLE
──────────────────────────────   ────────────────────────────   ─────────────
NarrationPlayer
  splits text into chunks
  (≤ 4000 chars, sentence
   boundaries)
        │
        │  HttpSpeechGateway
        │  POST /api/generate-speech
        │  { text, voiceName }
        ▼
   ────────────────────────►  speechRouter
                               SpeakTextUseCase
                               GeminiSpeechSynthesizer
                                 callWithModelFallback
                                      │
                                      │  generateContent({
                                      │    responseModalities: ['AUDIO'],
                                      │    speechConfig: { voiceName } })
                                      ▼
                                 ─────────────────────────────►  Gemini TTS
                                                                      │
                                      ◄──────────────────────── base64 PCM
                               { base64Audio }
   ◄────────────────────────
        │
        ▼
  decodeBase64  →  pcm16ToAudioBuffer(24 kHz, mono)
        │
        ▼
  WebAudioOutput → AudioBufferSourceNode → speakers
```

## Stage by stage

### 1. Chunking (browser)

`src/client/domain/textChunker.ts`

A document is split into pieces of at most **4000 characters**, cut on sentence
boundaries.

Three reasons, all of which apply to any TTS integration:

- Synthesis is **billed and rate-limited per call**.
- Long passages **time out**.
- Time-to-first-audio is what a listener experiences. Synthesising a whole
  article before playing anything would mean a minute of silence.

Splitting on sentence boundaries rather than a hard character count keeps the
seams from landing mid-thought. Seams are audible — the model has no context
across a call, so prosody resets at every boundary.

### 2. Request (browser → server)

`src/client/adapters/outbound/http/httpSpeechGateway.ts`

```ts
POST /api/generate-speech
{ "text": "...", "voiceName": "Kore" }
```

Wrapped in `ApiClient` with `SPEECH_RETRY_POLICY`: **15 attempts**, 40s wait on
a rate limit, 10s on "unavailable", 5s linear backoff step. Speech waits far
longer than an ordinary content call because rate limits here are expected
rather than exceptional.

### 3. Synthesis (server → Google)

`src/server/adapters/outbound/gemini/geminiSpeechSynthesizer.ts`

Models are tried **in order**:

| # | Model |
|---|-------|
| 1 | `gemini-2.5-flash-preview-tts` |
| 2 | `gemini-3.1-flash-tts-preview` |
| 3 | `gemini-2.5-pro-preview-tts` |

`callWithModelFallback` gives each model **3 attempts** with exponential
backoff (1s → 2s → 4s, capped at 8s), honouring the provider's own
`retryAfterSeconds` hint when it gives one, then moves to the next model.

Only **429 (quota) and 503 (overloaded)** are retried. A bad request, a missing
key or a malformed prompt fails identically on every model, so those surface
immediately rather than after a slow march through the list. A **404** — a
retired or not-enabled model — skips straight to the next entry, because Google
leaves retired names in `models.list` and a chain can rot with no config change
on our side.

Worst case before the caller hears anything: 3 models × 3 attempts, plus waits.

### 4. Playback (browser)

`src/client/adapters/outbound/audio/pcm.ts`, `webAudioOutput.ts`

The response is **raw 16-bit signed PCM, 24 kHz, mono**, base64 in JSON.

> **The gotcha worth copying:** it is *headerless*. `decodeAudioData()` cannot
> read it — there is no WAV/MP3 container to parse. The conversion to float is
> done by hand, in `pcm16ToAudioBuffer`: read `Int16Array`, divide by 32768,
> write into an `AudioBuffer` created at the right sample rate.

Get the sample rate wrong and the audio plays at the wrong pitch and speed
rather than failing — a silent bug.

### 5. Prefetch

`src/client/application/narrationPlayer.ts`

When chunk *N* starts playing, chunk *N+1* is requested in the background
(`prefetch`). Completed clips are cached in a `Map`; in-flight requests are
deduplicated so a seek does not fire the same call twice. A failed prefetch is
not reported — it is simply retried when playback reaches it.

### Voices

`src/shared/domain/voice.ts` — Gemini prebuilt voices, shared between client and
server because the browser offers the names and the server has to accept them:

`Kore` (default) · `Puck` · `Charon` · `Fenrir` · `Zephyr`

### Cards speak through a separate output

`src/client/application/cardSpeaker.ts`

Flashcards and quiz questions use the same `SpeechGateway` but their **own**
`WebAudioOutput`. Using `NarrationPlayer.load()` to read a card aloud would
*replace* the document being listened to. A card is an interruption, not a new
document.

## What leaves the device

For narration, per chunk: **the text of that chunk, and a voice name.** No
identifier, no cookie contents, no document title. The request does carry the
owner cookie (it is same-origin), but the payload itself is just text.

That text goes to **this server**, and from there to **Google**, under whatever
terms the Gemini API key is subject to.

**Narration is not the only thing that leaves.** Article cleaning, summarising,
PDF reading, study-pack generation and explanation grading all send document
text to Gemini too. Making TTS local would make *one of five* paths local. See
[TEXT-TO-SPEECH-ALTERNATIVES.md](./TEXT-TO-SPEECH-ALTERNATIVES.md).

## Failure modes seen in production

| Symptom | Cause | Where it is handled |
|---|---|---|
| Long pause, then audio | Cold start + first chunk round trip | Nothing to fix; design for it |
| `429 … free_tier_requests, limit: 20` | Free-tier quota exhausted | Model fallback, then a real error |
| Silence, no error | *(fixed)* a batch failure swallowed | `buildStudyPack` now throws |
| Wrong pitch/speed | Sample-rate mismatch | `NARRATION_SAMPLE_RATE` must equal `GEMINI_TTS_SAMPLE_RATE` |

The free tier is the practical ceiling: **20 requests** for
`gemini-2.5-flash-preview-tts`. At 4000 characters per request that is roughly
80,000 characters of narration per day — two or three long articles.

## Where to change it

`SpeechGateway` (browser) and `SpeechSynthesizer` (server) are ports:

```ts
// src/client/application/ports/speechGateway.ts
interface SpeechGateway {
  synthesize(text: string, voiceName: string): Promise<Uint8Array>;
}
```

Everything above them — chunking, prefetching, caching, playback, the card
speaker — depends on that signature and nothing else. A different provider, or
an on-device model, is a swap in `src/client/config/container.ts`. Nothing else
needs to know.

The one constraint a replacement must honour is the **sample rate**:
`WebAudioOutput` is constructed with `NARRATION_SAMPLE_RATE` and interprets the
bytes accordingly.
